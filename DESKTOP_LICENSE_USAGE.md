# Tiles POS Desktop, Owner, Client, and License Guide

## Overview

Tiles POS now works with 3 separate concepts:

- `owner`
  This is you, the software company owner. Owner is not controlled by trial or license.
- `client admin`
  This is the customer's shop admin account inside their local setup.
- `license`
  This controls whether a customer installation can use the software after trial.

The recommended flow is:

1. You install or prepare the normal Tiles POS EXE.
2. You log in as `owner`.
3. You create a client setup from the owner panel.
4. The system generates:
   - client admin login
   - installation-bound license
   - signed setup package
5. You give the EXE and setup package to the client.
6. The client installs the EXE, imports the setup package, and logs in directly.

## Owner vs Client

### Owner

- Owner can always log in.
- Owner does not need trial.
- Owner does not need a license.
- Owner can open `License Management`.
- Owner can create client setups and licenses.

### Client Admin

- Client admin belongs to one customer installation.
- Client admin is created by the owner before handoff.
- Client admin uses license/trial rules normally.

## How the Desktop EXE Works

The Windows EXE is an Electron desktop app.

When it opens:

1. It starts the local Node.js backend.
2. It opens the React frontend in a desktop window.
3. The backend connects to MongoDB using your configured `MONGO_URI`.

Important:

- The EXE is not fully standalone.
- MongoDB still needs to be available.
- If `MONGO_URI` is invalid or MongoDB is not running, the software will not work correctly.

## Recommended Real-World Client Delivery Flow

This is the best way to hand the software to a new customer.

1. Log in using your `owner` account.
2. Open `/license-management`.
3. Use `Provision Client Setup`.
4. Enter:
   - customer email
   - customer name
   - company name
   - customer phone
   - client admin name
   - client admin phone
   - client admin password
   - months
5. Installation ID is auto-generated for you.
6. Set `databaseLabel`.
7. Click `Generate Client Setup Package`.
8. Copy the generated setup package token.
9. Give the client:
   - the Tiles POS installer EXE
   - the setup package token
   - the client admin phone/password if needed
10. On the client machine:
   - install the EXE
   - open the app
   - open the `License` page
   - paste the setup package into `Import Provisioned Setup`
   - click import
11. The app will:
   - verify the setup package signature
   - adopt the provisioned installation ID on fresh setup
   - create the local admin account
   - activate the customer's license
12. Client can then log in directly.

## What the Setup Package Is

The long signed string generated by `Provision Client Setup` is not a Windows installer.

It is a signed import token that contains:

- customer details
- installation ID
- database label
- client admin login details
- license key
- expiry details

That token is imported inside the app from the `License` page.

## Trial and License Rules

### Trial

- A normal customer installation starts with a 30-day trial by default.
- Trial begins when the local license state is first created.

### After Trial Ends

- Non-owner users cannot continue until a valid license is activated.
- Protected usage is blocked.
- The app shows the `License` page.

### Owner Exception

- Owner is fully exempt.
- Owner can still access the software even if trial or license is expired on that machine.

## Installation ID

### What it is

`installationId` is the unique identity of one customer installation.

Example:

```text
tiles-c28b56b90c91
```

### Why it matters

The license is bound to this installation ID.

That means:

- the license belongs to one installation
- copying the same license to some other installation should fail
- you can identify which shop or system owns which license

### How it works now

- The owner panel auto-generates it.
- You can regenerate it from the UI if needed.
- During setup import, a fresh client machine can adopt the provisioned installation ID.

## Database Label

### What it is

`databaseLabel` is a human-readable name for the client database or shop installation.

Examples:

- `Tiles_POS`
- `varsha-main-shop`
- `madurai-branch`
- `gk-tiles-showroom`

### What it is used for

It is mainly for identification and reporting.

It helps you:

- know which client database belongs to which shop
- read owner dashboard entries more easily
- identify installations when many customers are using separate MongoDB databases

### What it is not

`databaseLabel` is not the security proof.

Actual verification is based on:

- signed setup package
- signed license key
- matching email
- matching installation ID
- valid expiry date

## How License Verification Works

When the client activates or imports setup:

1. The app verifies the signature.
2. The app checks the email.
3. The app checks the installation ID.
4. The app checks the expiry date.
5. If valid, the license is saved locally and the installation becomes active.

Because of that, even if different customers use different MongoDB databases, you can still verify whether the license belongs to that exact installation.

## How to Know Which Customers Are Using the Software

The owner dashboard can track customer usage using synced installation records.

You can monitor:

- installation ID
- company/customer name
- email
- database label
- current license status
- expiry date
- last seen time
- whether the setup was provisioned/imported

The relevant owner page is:

- `/license-management`

Dashboard sections include:

- `Expiring Soon Notifications`
- `Synced Installations`
- `Recently Generated Licenses`
- `Provisioned Client Setups`

## How Expiry Notification Works

The system already prepares expiry information.

You can see:

- current remaining days
- warning message
- expiring licenses in owner dashboard

Behavior:

- warning starts before expiry
- if the customer license is near expiry, the dashboard shows it in `Expiring Soon Notifications`
- local client license status also returns a notification message

## Email Configuration

There are 2 main email directions in this setup.

### 1. Owner notification email

Used when a customer sends a license request.

Configure:

- `LICENSE_OWNER_EMAIL`

If set, license requests are mailed to that address.

### 2. SMTP sender configuration

Used to actually send emails from the software.

Configure:

- `SMTP_HOST`
- `SMTP_PORT`
- `SMTP_USER`
- `SMTP_PASS`

Optional:

- `SMTP_FROM`
- `SMTP_SECURE`

### How email is used

- customer can send license request to owner
- owner can generate license and send it to customer email

### About admin email

Right now the client admin login is based on phone + password.

The provisioning flow stores:

- customer email
- client admin phone
- client admin password

If you want a separate stored email for each client admin user inside the local shop user record, that can be added later. At the moment, email is primarily used for customer/license identity, not for local user login.

## How to Build the EXE

From the project root:

```powershell
npm install
npm run desktop:dist
```

Output:

- installer: `desktop-dist\Tiles POS Setup 1.0.0.exe`
- unpacked app: `desktop-dist\win-unpacked\Tiles POS.exe`

## How to Run Without Installer

```powershell
npm install
npm run desktop:start
```

## Recommended Handoff Checklist

Before giving the software to a client:

1. Make sure MongoDB is ready on that client environment.
2. Log in as owner.
3. Generate client setup from `Provision Client Setup`.
4. Keep a record of:
   - customer email
   - company name
   - installation ID
   - database label
   - client admin phone
   - license months
5. Give the client:
   - installer EXE
   - setup package token
   - admin login details
6. Ask client to import setup package before first login.

## Current Limitations

- The setup package is currently pasted manually into the app.
- It is not yet a separate downloadable `.lic` or `.json` file.
- The installer is still common for all clients.
- Client-specific setup happens after install through the import flow.
